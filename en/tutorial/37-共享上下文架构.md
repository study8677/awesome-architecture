# 37 · Shared Context Architecture: Having Humans and Agents Read the Same Source of Truth

> One-line thesis: **The core interface of an AI-native organization is not meetings — it is shared context.** If humans and Agents cannot read the same goals, specs, decisions, tasks, code, feedback, and traces, collaboration falls right back into "relaying messages by word of mouth" and "guessing in the dark."

## 1. Context Is Not a Wiki Dump — It Is an Organizational Interface

Many teams assume "shared context" means setting up a company wiki or knowledge base. The result usually looks like this:

- Hundreds of documents exist, but nobody knows which one is current.
- Decisions were written down once, but later changes were never synced back.
- AI retrieves a pile of passages, unable to tell which ones are obsolete.
- The task tracker, codebase, customer feedback, and incident post-mortems are completely disconnected.

That is not shared context — it is a **document landfill**.

True shared context must answer three questions:

1. **Where is the source of truth?** Which document, ticket, ADR, or repo file is authoritative right now?
2. **Why was it decided this way?** Were the key trade-offs, rejected alternatives, and risk boundaries preserved?
3. **How can AI consume and update it?** Can Agents retrieve, cite, execute against, and write back to this context?

Shared context behaves like an **API interface**, not a static warehouse:

```
Human Judgment ──writes──▶ Specs / ADRs / Tasks / Rules
                                     │
                                     ▼
                         Agent Execution & Checks
                                     │
                                     ▼
                    Traces / Outputs / Feedback / Post-mortems
                                     │
                                     └──writes back──▶ Updated Context
```

The value of a good interface is eliminating repetitive hand-holding. Shared context does the exact same thing: neither humans nor Agents have to re-align from scratch on every task.

## 2. The Six Layers of Shared Context

An AI-native organization needs at least six layers of context:

| Layer | Typical Artifacts | Purpose |
|---|---|---|
| **Goal Layer** | Business objectives, customer problems, success metrics | Tells humans and AI *why* we are doing this |
| **Specification Layer** | PRDs, acceptance criteria, ADRs, `AGENTS.md` | Turns architectural and product judgment into enforceable constraints |
| **Task Layer** | Backlog, Owner, status, dependencies | Makes clear *who* owns *what* right now |
| **Asset Layer** | Codebase, design files, datasets, templates, Skills | Holds the concrete artifacts of execution |
| **Runtime Layer** | Agent traces, tool calls, CI runs, eval results | Makes visible what AI actually did and why |
| **Learning Layer** | Post-mortems, incidents, failure cases, best practices | Turns hard-won scars into organizational assets |

Among these six layers, the two most frequently neglected are the **Runtime Layer** and the **Learning Layer**.

Without runtime traces, you only see "the Agent produced an output" — you have no visibility into which inputs it read, which tools it called, or where it silently hallucinated.

Without a learning layer, every pitfall remains a private scar in one person's memory instead of becoming a guardrail for the next run.

## 3. Specification Is the Hardest-Working Layer of Context

As [Chapter 23](23-规格即架构约束怎么写给AI.md) established: **specification is architecture**. At the organizational level, this statement carries even more weight.

Most failures in human–AI collaboration happen not because the model is too weak, but because the specification is too vague:

```
Vague goal: "Help me optimize user growth"
AI's default fill-in: spam more notifications, run aggressive pop-ups, pester users

Clear specification:
- Goal: Improve Day-7 retention for new users
- Hard constraint: No forced pop-ups or unrequested push notifications
- Success metric: Day-7 retention +3%, user complaint rate unchanged or lower
- Acceptance bar: Experiment report must include cohort breakdown and negative side-effect analysis
```

The clearer the spec, the more AI acts like a senior teammate; the vaguer the spec, the more AI acts like an eager intern filling in dangerous defaults at high speed.

Organization-grade specifications must cover at least:

- Business goals and explicit **non-goals** (what we refuse to do).
- Quality attributes and measurable acceptance criteria.
- Permission boundaries and external communication boundaries.
- The reasoning behind key architectural decisions (ADRs).
- Mandatory repository/team rules that Agents must load before acting (`AGENTS.md`).

Specifications are never written once and frozen — they evolve continuously with every release and post-mortem.

## 4. Context Must Be Both Retrievable and Governed

Dumping every internal file into an AI's context window or vector index is not shared context — it is maximizing your blast radius and noise floor.

Shared context must satisfy two requirements simultaneously:

- **Retrievable**: humans and authorized Agents can quickly find the exact facts they need.
- **Governed**: not every Agent can see every dataset, and stale documents cannot silently override current rules.

```
                   Organizational Knowledge
                              │
            ┌─────────────────┼─────────────────┐
            ▼                 ▼                 ▼
       Public Docs       Internal Docs    Sensitive Data
            │                 │                 │
    Retrievable by     Authorized by     Scoped temporary access
       default          team / role        + full audit trail
```

Governance rests on four pillars:

1. **Tiered access control**: customer PII, employee records, financials, source code, and contracts must never be lumped into a single flat index.
2. **Source attribution**: whenever an Agent cites external web pages, customer emails, or internal docs, provenance must be attached.
3. **Freshness & lifecycle management**: an expired rule that AI still follows is more dangerous than no rule at all.
4. **Controlled write-back**: Agents must not overwrite the authoritative source of truth unchecked; high-impact write-backs require human review.

Shared context is not "the more data, the better" — it is **the right facts, under the right permissions, used at the right decision point**.

## 5. A Minimum Viable Shared-Context Architecture

At the MVP stage, you do not need a heavy "enterprise knowledge platform." A 3–5 person squad can start with a lightweight closed loop:

```
Customer Problem / Business Goal
               │
               ▼
PRD / ADR / AGENTS.md / Acceptance Criteria
               │
               ├──▶ Task Tracker: Owner, status, dependencies
               │
               ├──▶ Code / Design / Data Assets
               │
               └──▶ Agent / Skill Execution
                               │
                               ▼
                 Trace / Review / Eval / Post-mortem
                               │
                               └──writes back to rules & knowledge base
```

What matters in this diagram is not which SaaS tool you buy, but the **closed loop**:

- Goals flow into specifications.
- Specifications drive tasks and Agents.
- Agent outputs pass through review and evaluation gates.
- Outcomes and failure cases write back into the specification and rule layer.

As long as that loop is turning, even with plain Markdown files in a Git repo, your organization already has an AI-native context architecture.

## Chapter Summary

- **Shared context is an organizational interface**: it eliminates repetitive re-alignment between humans and Agents.
- **Six essential layers**: Goal, Specification, Task, Asset, Runtime, and Learning.
- **Specification is the hardest-working layer**: vague goals force AI to guess defaults at high speed.
- **Retrieval must pair with governance**: permissions, provenance, freshness, and write-back all need explicit boundaries.
- **Start with a lightweight loop, not a massive platform**: connect goals, specs, tasks, Agents, traces, and post-mortems into a closed loop first.

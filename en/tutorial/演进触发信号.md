# Appendix · When to Upgrade Your Architecture: Quantified Trigger Signals

> As [Chapter 08](08-架构决策记录与演进.md) emphasized: **never upgrade your architecture because it "feels old or ugly" or because "big tech companies use X."** Upgrade only when a quality attribute you genuinely care about is capped by a real, measured bottleneck.
> This cheat sheet turns that principle into **observable, quantified trigger signals** — only when you see these signals is it time to act.

> ⚠️ **Important: the numbers below are rules-of-thumb orders of magnitude, not iron laws.** Real thresholds depend on your hardware, data shape, and business tolerance. Treat them as "time to pay attention" alerts rather than automatic mandates. **The real justification is always: a quality attribute that matters to the business is hitting a measured bottleneck.**

---

## Reads / Writes / Storage: Data-Tier Signals

| Observed Signal (Rule-of-Thumb Range) | Likely Bottleneck | Common Remedy (see [05](05-数据与状态.md)) |
|---|---|---|
| Primary DB **CPU sustained > 70%**, read queries queuing | Read capacity saturated | Add **read replicas** + caching |
| Cache **hit rate drops < 90%**, heavy origin fallback traffic | Insufficient cache coverage or poor eviction/TTL policy | Tune cache granularity, TTL, and pre-warming; guard against penetration/breakdown/avalanche |
| **Single table reaches tens of millions to 100M+ rows**, or single DB **exceeds hundreds of GB** | Single instance outgrowing memory/storage; writes and schema changes slowing down | Consider **partitioning / sharding** (choose the shard key carefully) or archiving cold data |
| **Write QPS** nearing single-node limit; primary DB becomes the write bottleneck | Write capacity saturated (read replicas cannot help) | Sharding, write buffering/batching, or splitting out a dedicated write store |
| The same dataset is tortured by conflicting query shapes (OLTP transactions + full-text search + analytical aggregations) | One storage engine forced to do jobs it wasn't built for | Split read models by access shape (polyglot persistence / CQRS) |

## Latency / Performance: Experience-Tier Signals

| Observed Signal | Likely Bottleneck | Common Remedy |
|---|---|---|
| **P99 latency consistently breaches SLO** (while P50 looks fine) | Tail latency — a slow code path, lock contention, GC pause, or fan-out straggler | Trace the slowest hop and optimize that path specifically; don't waste effort tuning P50 |
| A heavy operation forces users to **wait > several seconds synchronously** | Synchronous request path doing work that should be asynchronous | Move to async processing + message queue peak shaving ([04](04-十大核心架构模式.md)) |
| Traffic shows **predictable sharp spikes** (ticket drops, flash sales, commute hours) | Provisioning for peak is too expensive; provisioning for average gets crushed | Queue-based peak shaving + autoscaling + (in extreme cases) virtual waiting rooms |

## Availability / Reliability: Stability Signals

| Observed Signal | Likely Bottleneck | Common Remedy |
|---|---|---|
| Business requires **stepping up availability** (99% → 99.9% → 99.99%) | Single points of failure or lack of redundancy cannot sustain another nine | Eliminate SPOFs, add redundancy, isolate fault domains, multi-AZ / multi-region |
| One component failing **takes down the whole system** (SPOF) | Unprotected single point of failure | Redundancy + automated failover + graceful degradation |
| A single fault **cascades widely** and recovery takes too long | No blast-radius isolation | Bulkheads, circuit breakers, timeouts, rate limiting, and load shedding |

## Organization / Engineering Velocity: The Most Overlooked Signals

| Observed Signal | Likely Bottleneck | Common Remedy (Often an Org Problem) |
|---|---|---|
| **Changing one place breaks three others**, releases slow to a crawl, nobody dares touch core code | Rotting module boundaries / tight coupling | Clean up module boundaries inside a **modular monolith** first; **you do not necessarily need microservices** |
| **Multiple teams block each other in one codebase**, release trains queue up | *People* scalability has hit its ceiling | This is the real trigger for microservices — but **align with team boundaries first** (Conway's Law, see [08](08-架构决策记录与演进.md)) |
| New hires take **weeks just to get oriented**, simple features touch dozens of files | Poor maintainability / missing architectural context | Refactor boundaries and document ADRs instead of piling on more features |

## How to Use This Table

1. **Measure first, judge second.** Talking about architectural upgrades without observability data (QPS, P99, cache hit rate, CPU, storage growth) is guesswork. **Instrument the metrics first.**
2. **Solve one bottleneck at a time.** Every architectural upgrade carries real cost and risk; it must buy relief for a quality attribute that is **currently bottlenecked** — never rewrite the whole stack at once.
3. **Write an [ADR](08-架构决策记录与演进.md) for every upgrade**: record which quantified signal triggered it, what you upgraded to, and what new complexity you accepted.
4. **If no signal has fired, don't touch it.** Upgrading without a trigger signal is almost always over-engineering or resume-driven development — remember [Chapter 09](09-架构品味.md): for individuals and small teams, the default architectural taste is **restraint**.

> In one line: **an architectural upgrade is an evidence-backed decision triggered by a real signal — not a periodic refactoring ritual, and not an impulse to chase new tech.**
